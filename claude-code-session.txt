  Endpoint: POST /v1/users/{userId}/sales con body {"units", "price_per_unit"}.
  Responde 201 con la venta.

  Cómo funciona la venta:
  - FIFO: recorre las compras del usuario de la más vieja a la más nueva. Saltea
    las que ya se vendieron completas y toma de cada una lo que necesita, así
    una venta puede llevarse varias compras y dejar la última a medias.
  - Ganancia por venta: realized_profit_usd = units × precio de venta − costo.
    El costo suma, por cada compra tocada, las units tomadas por el precio de
    esa compra. Puede dar negativa.
  - Qué guarda: cada venta queda en memoria con lo cobrado, el costo, la
    ganancia y el detalle de qué compras consumió y cuánto de cada una
    (consumed_purchases).

  Qué cambió en la compra: cada compra ahora guarda cuántas units le quedan
  (remainingUnits) y ese valor baja con cada venta. La respuesta del POST de
  compra incluye remaining_units.

  Agregados que no pediste:
  - Units insuficientes: devuelve 422 y no toca ninguna compra. Sin este
    control, el FIFO vendería menos units de las pedidas sin avisar.
  - Ventas simultáneas: sell es synchronized, para que dos ventas al mismo
    tiempo no vendan las mismas units.
  - Ceros en el JSON: los montos se muestran como 0.00000000 y no como 0E-8.

  Tests:
  - Unitarios:
    - PurchaseTest: consumo parcial, total y pidiendo más de lo que queda.
    - SaleServiceTest: venta que consume una compra a medias, FIFO entre varias

    - SaleRepositoryTest y SaleResourceTest.
  - Integración: SaleTestCase hace dos compras y una venta que consume las dos,
    y prueba el caso 422. También ajusté los tests de compra para
